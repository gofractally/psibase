# Description

After this PR, making new psibase releases becomes significantly easier / more automated.

There's basically four steps to making a new release:
1. open a PR to main that increments all version numbers
2. Merge that PR 
3. Merge the (autogenerated) `main->release/vX` PR
4. Publish the (autogenerated) release draft

# Details 

Here are more details on the four manual steps and what is happening automatically:

1. open a PR to main that increments all version numbers

CI detects the change to the PSIBASE_VERSION_* macros in ...psibase/version.hpp. Because it detects a version bump, it runs a dry-run of the crates publish on the PR. 

Unfortunately, dry running multi-workspace publishes in crates isn't great on our cargo version, so the dry run fails. So we detect the expected failure mode of the dry-run script (Only the expected error shape is allowed: "failed to select a version for the requirement") and treat is as a passing dry-run. When we upgrade to rust 1.90 we can improve this because there's new affordances for [publishing whole workspaces](https://www.infoworld.com/article/4060262/rust-1-90-brings-workspace-publishing-support-to-cargo.html). 


2. Merge the PR 

When merged, `cut-release.yml` detects the version bump on main. It creates 
`release/v<major>` at the pre-bump tip (if DNE), opens a `main → release/vX` PR.

3. Merge the `main->release` PR

I usually just push directly to the release branch (bypassing branch restrictions) because I'm lazy, but in this automated flow I wanted to leave this as a manual step instead of automatic because it's possible to patch the release branch directly which means it's possible for the `main->release` PR to have merge conflicts.

When merged, `cut-release.yml` tags the merge commit. It also verifies head major version matches `X` in the branch name `release/v<X>` before tagging. Tag name is resolved automatically to `v0.x.y-pre` when major is 0, else `vX.Y.Z`.

When the tag is pushed, the pre-existing flow runs:
* `ubuntu-builder.yml` builds at the tag
* We auto-generate the changelog.
  * **New: The workflow was updated to automatically prepend the standard disclaimer to the top of any v0 release**
* Create a draft GH release (With attached SDK artifacts)

4. Publish the release

This is still a manual step. It's the same manual final check we are used to.

After publishing, `on-release.yml`:
* Dispatches Docker image builds
* Sends telegram notification
* **New: Runs rust/scripts/publish.sh to crates.io using CARGO_REGISTRY_TOKEN**
